## Архитектура (не ломать)

- `mycar/config.py` — **единственный источник** правды: профиль машины, пути, пороги сессий (`COLD_COOLANT_MAX_C=40`, `WARM_COOLANT_MIN_C=80`), нормативы `NORMS`. Все пороги и цифры менять только здесь; `analyze.py` сверяет с ними, docs ссылаются на те же значения.
- `mycar/sensors.py` — список опрашиваемых Mode-01 PIDs (имя, hex-pid, число байтов данных) + декодеры. Порядок списка = порядок колонок CSV. Байты данных считать **без служебных** `41 xx` (однажды тут была бага — см. «Уроки»).
- `mycar/elm.py` — **raw pyserial-драйвер** (транспорт USB/Wi-Fi): одна мягкая инициализация (ATZ, ATE0, ATL0, ATS1, ATH0, ATSP6), никаких автодетектов скорости/протокола, чтение до `>` промпта. Декод CVT — в `toyota.py`.
- `mycar/toyota.py` — знания из реверса Car Scanner (`../rea`, см. `docs/07`): кандидатный декод ATF/CVT (`21D9`/`2182`, варианты SBI/DL из каталога), мульти-запросы Mode 01, DTC-декод + справочник Toyota-priority (`data/toyota_dtc.json`, 5883 кода). Всё опциональное: без ответа ЭБУ молча возвращает None. **Не ломать базовый путь ради этих функций.**
- `mycar/elm_ble.py` — **BLE-драйвер (bleak)**: сервис `0000fff0`, характеристика `0000fff1` (write+notify на одном канале; адаптер сам эхом возвращает отправленное). Синхронная обёртка над asyncio-лупом в демоне-треде, интерфейс тот же, что у RawELM. Автоскан `scan_ble()` ищет `fff0`/`18f0`/имя с OBD/ELM.
- `mycar/connection.py` — фабрика: **BLE в приоритете** (адрес из `.env` `MYCAR_BLE_ADDRESS` → автоскан `fff0`/`18f0`), потом serial-кандидаты, `ble:<addr>`, `socket://` (Wi-Fi), sim. Ошибки — внятные (`ElmError`), а не сырые стеки.
- `mycar/sim.py` — симулятор с тем же интерфейсом (`query_mode01/query_cvt_and_raw/close`), что и RawELM/ElmBLE. Любые изменения логики capture проверять на sim, а не на машине.
- `mycar/capture.py` — только цикл записи (CSV + meta JSON) + авто-реконнект при потере линка (до 20 раз, инкрементальный ts не сбрасывается). Без анализа внутри. Остановка SIGTERM/Ctrl+C корректно закрывает порт (дешёвые клоны зависают, если процесс убить жёстко).
- `mycar/dashboard.py` + `dashboard.html` — дашборд: поток `State.push()` из capture → WS-клиентам; страница статична (данные только через WS), Chart.js с CDN. Сервер-демон-тред, TTL 1 ч, сам освобождает порт. `dashboard.html` читается при старте процесса — правки страницы требуют перезапуска capture.
- `mycar/analyze.py` — только чтение logs/ и запись stats/. Без опроса ЭБУ.
- `mycar/db.py` — SQLite-зеркало логов (`logs/chr.db`): таблицы `sessions` + `samples` (по колонкам CSV). capture зеркалит каждую сессию сам; `python -m mycar db` доимпортирует пропущенные CSV и печатает кросс-сессионную сводку (тренды: ХХ-обороты, LTFT, время прогрева по всем сессиям).
- `mycar/cli.py` — тонкий argparse-слой + SIGTERM-обработчик для graceful-остановки.
- `obdii_test/ble_elm.py` (рядом, вне mycar) — быстрый BLE-тест транспорта (ATZ + 0100 + 010C).

KISS/DRY-инварианты: нет второго списка PIDs, нет дублирования порогов в коде, нет логики в CLI, нет OBD-библиотек в рантайме (только pyserial + bleak + fastapi/uvicorn). Магические числа — в `config.py`/константы модуля; варианты поведения — в enum (`toyota.ObdMode`, `toyota.DtcSystem`); машинные настройки (BLE-адрес донгла, BT-пин) — **только в `.env`** (см. `.env.example`), в код и git они не попадают.

## Железо и транспорт — выжатые уроки (читать перед любыми BT-манипуляциями)

Адаптер: «ELM327 v1.5» клон, имя `OBDII`, двухрановый (classic SPP + BLE FFF0), BLE-адрес и BT-пин — в `.env` (приватно, `MYCAR_BLE_ADDRESS`/`MYCAR_BT_PIN`).

1. **Работающий транспорт — только BLE.** Классический SPP-профиль этого клона на macOS кривой: RFCOMM коннектится, данные не идут, адаптер после таких сессий зависает наглухо и реанимируется только по питанию. Не открывать `/dev/cu.OBDII` для этого донгла вообще и не делать `blueutil --connect` — каждое касание SPP вешает его.
2. **BLE — как CarScanner на iOS.** Скрипт `ble_elm.py` + драйвер `elm_ble.py` дают стабильные данные (проверено: часы ХХ 726–736 rpm). Если донгл «умер» — перевтыкнуть питание; BLE сам переподнимается.
3. **iPhone-конфликт:** донгл держит одного клиента. CarScanner на iPhone может перехватывать его сразу при подаче питания → Mac не видит данных. Тест «на компе не коннектится, а на телефоне работает» = донгл занят iPhone.
4. **Прошивка клона — функционально-ограниченная (ключевой факт):**
   - работает: ATZ/ATE0/ATL0/ATS1/ATH0/ATH1/ATSP6, Mode 01 (стандарт), функциональная адресация 7DF; отвечают ДВА блока — `7E8` и `7E9` (7E9 — зеркало/гейтвей: те же значения ECT/IAT/RPM, своего блока данных нет);
   - **не работает:** `ATSH` — принимается с фейковым OK, но TX-заголовок не меняется (доказано тестом `ATSH7E8 + 010C` → ответы всё равно от 7E8/7E9); `ATCAF0` + сырые CAN-кадры — тоже не идут. Следствие: **физическая** адресация невозможна, а значит **CVT-темп недоступен вовсе**: обходы `01B4`/`21D9`/`2182` проверены на машине 2026-11-24 — все `NO DATA` (полный отчёт: `docs/07`). Колонки `cvt_temp` остаются пустыми — это ограничение железа, не баг софта.
   - **маска поддержки PID врёт не всегда, но врёт:** `0x5C` (масло) не advertised, но отвечает; `0x0B` (MAP) и `0x23` (ТНВД D-4T) не отвечают и по факту. Реальный список — `docs/07`.
5. **Паттерн деградации линка:** BLE-соединение иногда рвётся через ~30 с опроса — capture сам переподключается и продолжает сессию (reconnect-логика). Не «лечить» это перевтыканием по кругу.
6. **`CAN ERROR` на всех протоколах ≠ поломка** — это спящая CAN-шина: старт-кнопка нажата один раз (ACC), ЭБУ не проснулись. Зажигание ON = двойное нажатие без педали тормоза (на приборке загораются АКБ/масло/Check Engine). `NO DATA` — другое: шина живa, ЭБУ не отдаёт PID.

## Что НЕ делать (проверено болью)

- Не запускать python-obd / py-obdii против этого клона: их агрессивный инит (`\x7F\x7F`-флуд baud-детекта, протокол-автосан) вешает донгл. В рантайме mycar их нет и не надо.
- Не убивать capture `kill -9`/`pkill` без нужды: порт остаётся открытым, донгл зависает до перевтыкания. `Ctrl+C` / SIGTERM — безопасно (graceful-обработчик).
- Не ходить в SPP-сопряжение донгла (System Settings/`blueutil --pair`): ломает рабочую BLE-сторону. BLE не требует сопряжения в macOS.
- Не верить «OK» от AT-команд клона без проверки на шине: `ATSH`/`ATCAF0` отвечают OK и не действуют.
- iOS CarScanner при тестах: выключать Bluetooth на iPhone, иначе он молча забирает донгл.

## Данные

- `logs/` — append-only: сессии `<stamp>_<mode>_NGX10.csv` + `.meta.json`. Не переименовывать и не редактировать задним числом; тестовые сим-сессии удалять, а не править.
- `stats/` — генераты analyze; можно чистить и пересоздавать.
- CSV-столбцы: `ts` + `sensors.COLUMNS` (rpm, speed, coolant, oil_temp, iat, map, baro, maf, load, stft, ltft, rail_p, timing, throttle, voltage, runtime, cvt_temp, cvt_raw). Пустое значение = «ЭБУ не отдал PID» — это не ноль. `cvt_raw` хранит сырые байты `21D9`/`2182` — по нему сверяются варианты декода из каталога (см. `docs/07`).
- MAP (0x0B) и rail_p (0x23, ТНВД D-4T) этим ЭБУ не отдаются (probe 2026-11-24) — boost считается как `map−baro`, пока map None будет пусто. `0x5C` (масло) при этом работает, хотя маска поддержки его не показывает.

## Нормативы

- Нормы — `docs/03-cold-start-norms.md` + `mycar/config.py::NORMS`; полный список доков и «кто где живёт» — в навигаторе вверху этого файла.
- Реверс Car Scanner лежит в `../rea` (не трогать, только читать): вход `rea/docs/README.md`, для C-HR — `toyota_chr.md`, `toyota_pids_catalog.md` (раздел B0), `toyota_dtc_protocol.md`. Данные оттуда — **не проверенная реальность**: интегрировать только через fallback-пути, сырьё сохранять всегда.
- При интерпретации логов НЕ выдумывать пороги для «не нормированных» параметров (MAF на ХХ, время прогрева при 0 °C, низкий контур топлива, MAP) — оценивать по динамике.
- Trims читать только в контексте: петля, температура, обороты. Первый живой лог показал **LTFT −14.1 % на прогретом ХХ** — за пределом ±10 %, разобрать в сводке после холодного пуска (не выдумывать причину заранее: JDM-калибровка / подсос / форсунки — проверить по данным).

## Среда

- venv: `.venv/` (python 3.14; зависимости: `pyserial`, `bleak`, `fastapi`, `uvicorn[standard]` — см. `requirements.txt`). Запуск: `python -m mycar …` из `mycar/`.
- `.env` — машинные настройки (`MYCAR_BLE_ADDRESS`, `MYCAR_BT_PIN`); копируется из `.env.example`, в git не входит. Без `.env` работает автоскан BLE.
- Право Bluetooth macOS выдаётся терминальному приложению (Terminal/iTerm/VS Code), не python.
- Поиск в интернете — через `opencli google search "..." -f json` (searxng нестабилен).

## Проверки перед сдачей изменений

```sh
python -m mycar doctor                                             # окружение
python -m mycar capture --sim --sim-speed 60 --max-minutes 0.6     # запись, warm-детект
python -m mycar analyze                                            # сводка
python -m mycar db                                                 # SQLite-зеркало + кросс-сессии
python -m mycar capture --sim --no-dashboard --max-minutes 0.1     # без дашборда
python -m mycar probe --sim                                        # Mode-21 меню + кандидаты декода
python -m mycar dtc --hex "7E8 06 43 02 01 33 02 44" --mode 03     # DTC-декод без машины
```

Живая проверка транспорта (машине нужно зажигание ON, лучше двигатель):

```sh
.venv/bin/python ../obdii_test/ble_elm.py                          # ATZ + 0100 + 010C по BLE
```

Изменение в `sensors.py`/`config.py` должно пройти полный прогон на sim, включая анализ прошлых CSV (обратная совместимость колонок).

## История: неудачи → решения (чтобы не повторять)

1. **«Не могу узнать пин»** → macOS спарил сам; пины клонов на будущее: 1234, 0000, 6789, 1111.
2. **python-obd: «Failed to set baudrate» / «No connection to car»** → байт-флуд `\x7F\x7F` в auto-baud ломается через BT; игнор — отказ от библиотеки в пользу raw.
3. **Донгл виснет после каждого жёсткого kill / python-obd / py-obdii прогона** → только power-cycle реанимирует; graceful close в capture + отказ от библиотек.
4. **«Failed to connect» / SPP молчит** → донгл занят CarScanner на iPhone (один клиент) или SPP-профиль клона сломан; решение — BLE.
5. **Донгл пропадает из `/dev/cu.*`** → нормальное поведение: BT-SPP-нода исчезает при обрыве; BLE-адрес постоянный.
6. **BLE найден, но `scan_ble` цеплял чужие FFF0-устройства** (лейбл «Funcl AI», «smartBox») → сканеру требуется FFF0/18f0 + приоритет имени OBD/ELM.
7. **`ElmBLE._on_drop()` TypeError** → bleak вызывает callback с аргументами; сигнатура `(*_args)`.
8. **Capture: «7 queries failed in a row» через ~30 с** → деградация BLE-линка; авто-реконнект без прерывания сессии.
9. **`query_mode01` возвращал None при живых данных** (`41 05 7E` в логе, а данных нет) → путаница «ожидаемые байты»: в POLL хранить число байтов **данных**, без `41 xx` служебных.
10. **`2182` молчит на всех адресах, хотя `010C @ 7E0` отвечает** → у клона TX-заголовок не меняется (ATSH-заглушка), физической адресации нет; кастомные Mode-21 непрочитаемы. Подтверждение: `ATSH7E8 + 010C` → отвечают оба блока как на функциональный запрос.
11. **Теплая теория «7E9 = TCM со своей CVT-температурой»** → прочёс стандартных PIDs показал: 7E9 зеркалит 7E8, эксклюзивных данных нет.
12. **APK CarScanner с APKPure** → Cloudflare-challenge, curl не проходит; прямые зеркала (apkcombo) дают 403. Если понадобится REA — качать через браузер/эмулятор Android или просить пользователя вытащить APK с телефона.
13. **Реверс Car Scanner (`../rea`) показал обходы ATSH-заглушки**: ATF/CVT-датчик существует в трёх видах — **`01B4` (Mode-01 расширение Toyota, функциональный — лучший шанс на клоне)**, `21D9 @7DF` (JOBD JDM CAN) и `2182 @7E0`. Интегрировано fallback-путём (`probe_cvt`: 01B4 → 21D9 → 2182 → None), с кандидатным декодом и сырьём в `cvt_raw`. **Итог проверки на машине 2026-11-24: всё `NO DATA` — CVT-темп через этот клон недоступен.**
14. **Mode-01 расширения Toyota не ограничиваются стандартом**: `01B4` (ATF), битовые маски `0100…` показывают реальную поддержку PID, Mode 09 (0902/0904/090A) даёт VIN/CalID — всё это идёт функционально, без ATSH. K-Line-расширения (`01F4/01F7/01FE`) и дизельные `019x` из профилей к нашему CAN-бензину не применимы.
15. **Ctrl+C терял meta/БД сессии** (save-блок шёл после цикла и был недостижим при исключении; сам CSV оставался) → сохранение вынесено в `finally` (`capture.save_session`), проверено SIGINT-тестом. И **уборка логов glob'ом `logs/2026*` удалила живую сессию вместе с сим-мусором** → чистить только по полным именам файлов; потерянный CSV восстановлен из консольного лога (9 колонок: ts/coolant/oil/rpm/maf/stft/ltft/cvt).
